# P1.5 implementation handoff

P1.5 working direction · 25 October 2026 · Audience: P2–P4 implementers.
The user supplied [this UI reference](references/user-ui.png), then selected a cave-like theme with grey UI tones. Keep its board-first layout, lower-right icon toolstrip, lower-left selection info and top-left five-gem summary. Detailed cave-background styling remains deferred. Values below are design choices, not measured gameplay facts.

## Camera and material

Support two orthographic camera modes behind a visible toggle. The default **Isometric** view uses **45° azimuth and 35.264° elevation** above the board. **Top** uses **90° elevation**, looking straight down, with a square north-up grid at zero rotation offset. Use a stable board-north camera up vector in Top; the view direction and up vector must not be parallel. At the default fixed preset, this is true isometric: ground diamonds have a 1.732:1 width-to-height ratio. Free azimuth rotation changes that screen-space shape. Reject 2:1 dimetric (30° elevation): true iso reveals more cell depth and limits overlap. Board coordinates stay fixed when the camera rotates. Start with the angle locked at the preset. The lock icon holds the current angle; unlocking and activating Rotate allows horizontal orbit without changing elevation. In Top, this becomes rotation in the board plane. In Rotate mode, dragging turns the board and must never place or keep a gem. Locking again returns normal drag-to-pan. Provide turn-left/right controls in the camera flyout as keyboard/touch alternatives (90° turns), plus Reset view to return to the preset. Orbit changes only the relative rotation offset, not the logical grid or sim state. Pan and zoom preserve the selected cell. Fit the camera using the projected playable cells and measured HUD exclusion rectangles. A full-screen canvas can draw scenery beneath panels, but no playable cell or selected target may hide behind one. Dock or collapse the inspector and refit when corner placement cannot keep cells clear. Never hard-code HUD margins. Apply the same cell picking, path/range overlays and HUD exclusion rules in both modes.

The toolstrip is visually icon-only. A view icon switches Isometric / Top; lock and rotate icons expose Fixed angle / Rotate state. Every icon has an action-specific accessible name, visible keyboard focus and a tooltip on hover/focus; touch users can read tool names in a tool-help popover. Locked/active states use shape or outline as well as tone. Keep focus on the active control after switching and announce the new view or lock state once. The camera flyout contains labeled controls, including turn-left/right, Reset view and zoom; the icon-only rule applies to the compact toolstrip, not to this accessible flyout.

Switching Isometric / Top preserves the selected gem, keyboard cursor, logical pan anchor, relative rotation offset, lock state and zoom relative to each mode's fit. It never sends a simulation command, restarts a wave or changes a placed gem. Refit for the new projection, keeping selection clear of panels. Reduced motion switches immediately. During a camera transition, disable cell activation until picking agrees with the displayed projection. Use board-ground picking in both modes. Top-view mesh cuts and upright type stamps must remain distinguishable; the top-view studies use diagrammatic icons, not finalized mesh tops.

Flat-shaded, opaque low-poly meshes use one warm directional light and a neutral fill. Avoid metallic reflections, bloom, noisy textures and transparent gems. Pale slate cells and a neutral slate-grey surround keep the focus on gems. Detailed background terrain, vegetation, water, cliffs and other dressing remain deferred; the required entrance/goal connections are specified below. Future scenery stays outside playable cells. A small contact shadow anchors each model. Low graphics can remove shadows without losing selection or identity. These are rendering defaults, not Classic rule changes.

## Model scale and readable gems

One cell is one world unit. The user's tower-like revision replaces the earlier socket-only model with a broad base, masonry shaft and gem crown. In the [current basic tower study](model-study/README.md) each gem type has its own shaft profile and facet count, so type reads in grayscale. The Diamond is a coursed square tower whose claws hold a large brilliant cut; it gains detail with each quality step. Each tower's head (prongs or claws, and gems) turns toward the creep it attacks: `userData.aimAt(x, z)` faces the head to a board point and tips its gems about 10° toward it; `aimAt()` rests it. P2 owns target choice and turn easing; the occlusion and creep-visibility budgets below hold with the head aimed at any neighbouring cell. Each tower stands on a masonry pier built by the wall generator with `towerBase: true` and the same world seed/neighbours, so its arms and global brick bond join adjacent walls and animate with them. Quality scales the tower above that base uniformly: widths **0.38 / 0.44 / 0.50 / 0.56 / 0.62 / 0.68**, height caps **0.68 / 0.78 / 0.87 / 0.97 / 1.06 / 1.16**. Walls remain at most **0.20 cell** high. They are low castle walls with broad bevelled blocks, two staggered courses, continuous coping and chunky battlements. World-aligned brick coordinates preserve mortar phase and colours across cardinal neighbours; straight/end sections are narrow, while corners/junctions and tower footings use broader piers. The connected pattern is procedural geometry/vertex colour, without raster textures. See [the wall contract](model-study/WALLS.md). A raycast probe at four quarter-turns and one axis-aligned angle shows chipped and flawed towers hide no neighbouring cell centre at creep height; normal to huge towers hide exactly one, the cell diagonally behind. P2 must fade or outline the occluding tower when that cell holds the selection, cursor or a creep. Creeps scale in proportion to VPK `ModelScale` (1.0–2.2 for waves, 2.2–5.0 for bosses, up to 6.0): body length is 0.36 × ModelScale cell and height 0.66 × length, so the original size ratios hold and bosses read at 1.5–2 cells. Walls on either side of a one-cell corridor leave 1.38 cells clear beside a huge tower; ground creeps up to 5.0 fit. Bosses can hide towers behind them; when a tower is selected, P2 must fade or outline creeps covering it. The smallest creep's top stays visible over any single tower in the four default isometric views; during free rotation, an axis-aligned view can hide it behind one flawless-or-larger tower. Air units fly at 1.35 cell with a ground shadow; picking and targeting use the shadow cell. Health bars are DOM or sprite overlays drawn without depth testing, anchored just above each creep body (`userData.healthBarY`); bosses and the selected creep also show their HP number. Collision and pathing keep the VPK hulls; this scale is presentation only. Creep designs, animation, health bars and crowded-board performance remain unvalidated.

Use the eight silhouettes in [gems.svg](gems.svg). Their fixed HUD stamps follow VPK codes: diamond D, sapphire B, topaz Y, ruby R, emerald G, opal E, aquamarine Q, amethyst P. The six quality tiers are chipped, flawed, normal, flawless, perfect and huge. Display the full name and a numeric tier in the inspector. A billboard type stamp remains upright through camera rotation when zoom permits. At overview zoom, use selection and the inspector instead of promising tiny silhouettes can be identified.

Draw selected/focused cell rims above terrain. Keep ground hitboxes independent of mesh height. On touch, tap selects and a labeled action confirms; a mistaken tap must not build, keep or sell. At precise zoom, neighboring cells and creeps must remain visible around a maximum-tier tower at all four camera rotations. If an oversized special tower fails this test, simplify its silhouette. Effects stay short and never cover a cell cursor; reduced motion removes camera easing and decorative effects.

## HUD and input

Desktop: full-screen arena under a 64 px status bar. The top-left panel summarizes the **five gems placed this round**, with one slot per placement. The lower-left info panel follows the current selection. The lower-right toolstrip contains **icons only**. Keep 48 × 48 px targets, 8 px gaps and opaque charcoal surfaces. The study shows ten icons; fit those actually supported by the current phase and move overflow to More instead of shrinking targets. Tablets can collapse the info panel. Phone portrait uses two status rows, the five-slot summary, board, compact icon row and selection sheet. Short landscape reserves a scrollable side inspector and sticky action row. Safe areas and measured HUD exclusions apply in both camera modes.

A placement slot shows the actual placed gem's silhouette, type code and quality. Its accessible name includes ordinal position, full gem name, quality and board cell. Activating a filled slot selects that gem by stable entity ID, moves the board cursor to it, brings it into the safe visible board area, and updates the info panel. It does not place, reroll, keep or combine. Empty slots are disabled and say “not placed”. Both slot selection and board selection show the same active outline. Keep placement order stable during the round; if the entity is removed or transformed, update the slot from current sim state and never select a stale ID. At the next placement round, replace the summary from the new round's placements; do not carry old IDs forward. The user explicitly requested selectable slots; this supersedes the earlier non-interactive-progress note.

The lower-left info panel reflects the selected gem, stone, creep or empty cell. For gems, show name, type/quality, coordinates, combat/ability details and valid actions from current game data. Show recipe ingredients only where actual recipe data exists. When nothing is selected, show brief placement guidance. Illegal actions stay disabled with a readable reason; for example, Keep cannot be used before all five gems are placed. Mockup placements and their selected state are illustrative, while board checkpoints and fixed walls remain source-verified. Selecting a summary slot must retain keyboard focus and announce the selection; it must not unexpectedly move focus into the info panel. Closing a panel restores focus to its opener. HP, phase and pause state remain visible.

The DOM owns menus, controls, descriptions and status announcements. Provide one keyboard board cursor with arrow navigation, Enter to select and Escape to close the top panel. Keep screen-relative arrows consistent after rotation and announce logical cell coordinates. Announce selection, invalid actions and phase changes, not combat ticks. Preserve keyboard focus when the HUD updates. A DOM cell inspector must expose the same selection and commands to assistive technology; a canvas label alone is insufficient.

## End-of-run summary

[User reference](references/user-end-card.png), received 25 October 2026. Show a modal summary when the castle falls or the last wave clears. Use the HUD palette, Main menu and Play again actions, and keyboard focus on Play again.

- **Header:** result, mode and one-line cause.
- **Score card:** final score with its parts, and "New best" against the local best. Use the Classic score definition; the VPK ranks by kills. Do not invent a formula.
- **Totals grid:** waves cleared, kills, leaked, damage, towers, build level, accuracy and time.
- **Per-wave chart:** one bar per wave on a log scale, with Damage / Gold / Castle / Kills tabs. Hovering or focusing a bar shows that wave; give the chart a text summary for assistive technology.
- **Top towers:** the five towers that dealt the most damage, with the gem icon, name, damage, share, kills and combine wave. Add a damage-type split bar.
- **Highlights:** biggest hit, hardest wave, longest wave, leaks, critical hits, dodges (evasion), gold stolen by thieves, gold spent, and towers built with combines, downgrades and removed stones. Each highlight appears only when its Classic mechanic exists: prayers, thieves, evasion and crit do.
- **Gems placed by quality:** six bars, chipped to huge, plus a prayer count and cost.
- **Best runs:** a local top list per mode, marking this run. Stored on the device only.

Every value comes from simulation events, not from the renderer. The sim must record per-wave damage, kills, leaks, gold and castle HP; per-tower damage, kills and damage type; hits, crits and dodges; thief gold; and build actions. This screen is P3 or later; P1.5 records the layout only.

## Implementation gate

P2 checks isometric and top-down projection, four cardinal rotations and an intermediate free angle in both modes, cell picking and camera fit at 1440×900, 768×1024, 390×844, 320×568 and 844×390. Check Fixed and Rotate modes, locking at a non-default angle, reset, drag/pick separation, and gesture-free rotation controls. Repeatedly toggle views at fit and zoomed-in scales, with a selected corner cell, keyboard cursor and open inspector; selection, rotation, pan anchor and relative zoom must not drift, no gem or wave may change, and pointer picks must match the shown grid. Verify the toggle is keyboard/touch accessible and reduced motion switches immediately. P3 checks that each of five slots selects the same gem as the board, empty/stale/removed slots cannot act, selection updates the info panel, both selection paths announce consistently, and round transitions replace old slot IDs. It also checks legal/illegal actions, long translated labels, keyboard/assistive paths, visible focus and contrast. P4 checks crowded cells, effects and low graphics. Use actual VPK map geometry, rules, costs and labels. The studies use the verified current GemTD board geometry from [board-reference.json](board-reference.json); [BOARD.md](BOARD.md) records its coordinates and differences from original VPK anchors. P2 must use the original world anchors for Classic, not substitute the screenshot-derived grid. HUD values remain illustrative; no new draft tray, stat value or Classic mechanic is defined.
